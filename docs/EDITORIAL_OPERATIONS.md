# 朝のブリーフ：編集・配信契約（Phase 3A-Fix）

このPRは準備用です。**マージ、本番公開、毎朝タスクの新設・変更は別承認**です。
`config/editorial.json` が詳報の唯一の正本。RSS の `data/latest.json`・アーカイブとは別に保持し、既存の画面・CSS・3記事を変更しません。追加のAI API・有料サービス・秘密鍵は不要です。

## 編集判断（Dots・レビュー担当者）

優先分野は、①日本株・投資・企業決算、②日本/世界経済・金融政策・金利・為替、③重大な国際情勢・政治・社会、④AI・半導体・重要技術、⑤重大なサイバーセキュリティ、⑥自治・税制・防災・生活制度、⑦その他の重大な社会的影響、の順です。ただし緊急性と読者への影響を優先し、分野の順位だけで採否を決めません。

候補ごとに重要性・影響範囲・新規性・読者との関連性・情報の信頼性を各0〜3点で記録し、`2×重要性 + 影響範囲 + 新規性 + 関連性 + 2×信頼性`（最大21点）と採否理由を残します。信頼性0点は採用しません。同点では一次資料が確認できるもの、次いで新規性を優先。同じ事件・決算は続報を既存IDに統合し、RSSの新着順・クリック数だけで選びません。この採否判断は編集作業であり、スキーマがニュース価値を保証するものではありません。

詳報は「何が起きたか／背景・経緯／仕組み／重要数値／複数の見方／投資・経済・社会への影響／今後の注目点／用語／出典」を扱います。該当しない項目は理由を記し、穴埋めの推測をしません。重要度に応じて文章量を調整し、比較表・棒グラフ・時系列を使います。表示対応は既存の `text`・`table`・`bars`・`flow`・`timeline` ブロックを再利用します。

- **事実**：出典中のどこで確認したかを明記。発表日時と確認日時を分ける。
- **分析**：筆者の解釈と明記し、根拠・異なる見方・限界を示す。
- **予測**：会社予想／市場予想／独自の見通しを区別し、前提と不確実性を示す。未来を事実扱いしない。
- **決算**：連結範囲、対象期間、通貨・桁、実績／会社予想／市場予想を揃えて比較。前年同期と直前四半期、累計と単独を混同しない。日経225採用は公式構成銘柄を確認し、会社名・記事から推測しない。市場予想が未確認なら「未確認」とし、超過・未達を判定しない。
- 重要数値は出典と構造化メタデータを対応づけ、算出値は計算式・入力・単位・丸め精度を残す。未確認の重要数値を確定事実として掲載しない。
- 未公開の個人情報・投資情報・認証情報を原稿やログに含めない。機械的な検出だけに頼らず、人間が公開対象を確認する。

## 原稿の受け入れと判定

既存JSONの描画フィールドを維持し、新規原稿にはv2の確認・更新履歴・分類・数値メタデータを付けます。正確な必須項目と合成見本は `tools/editorial.py` とそのテストを正とします。既存3記事の特例は記事ごとの完全一致ハッシュに限定し、同じIDの改変や新記事に旧形式を流用して検査を回避できません。

判定を混ぜません。`sourcecheck.status=passed` は照合担当者の記録要件の合格であり、`source_truth=not_verified_by_program` を明示します。`editorial_judgment=recorded_attestation` も人による判断の記録です。既存3記事の免除から新たな照合済み判定は導きません：

| 判定 | 検証するもの | 保証しないもの |
|---|---|---|
| 形式 | 必須項目・型、ID、日時/TZ/順序/期限、URL、参照番号、表の形、重複 | 記事の真実性 |
| 数値整合性 | 有限の数値、単位/期間/実績・予想、算出値の再計算 | 元の数値が出典と一致すること |
| 出典照合 | 担当者の照合結果・根拠・確認日時を記録 | 自動でリンク先を読んだ、真偽を確認したという保証 |
| 編集判断 | 採用/保留、根拠、不確実性・見方の区別を記録 | ニュース解釈や投資判断の正しさ |

新規ブロックの見出しに `事実`・`分析`・`予測` を明記し、既存画面のまま区別を表示します。数値表の各数値セルは `numeric_cells`、棒グラフの各行は `metric_ids` で `metrics` に結び、表示値・単位・期間・実績/会社予想/市場予想の表示を一致させます。`ratio_percent`・`growth_percent`・`difference`・`sum` は2入力を再計算し、指定桁の四捨五入（half-up）と照合。%同士の差はptです。自由文の数字の完全抽出・真偽・因果関係は自動保証せず、未確認の構造化数値は掲載拒否します。対象期間を持つ数値には期首/期末を、金額には通貨を必須とします。入力と既存記事を結合した最終保存JSONを実際の整形形式でUTF-8化し、読み込みと共通の2,000,000バイト以下（2MiBではない）を要求します。超過は一時ファイル作成前に拒否し、元ファイルのバイト列・SHA256を保持します。期限切れの保管記事は保持しますが、追加/更新する対象の期限切れは拒否します。

### Phase 3A-Fix：数値・順位・配信日の具体的契約

- 表の数値は座標 `numeric_cells(row,column,metric)` に対応する列見出しと第1列の行見出しで、指標名 `metrics[].label`・期間・実績/会社予想/市場予想を照合します。別行、別列、表全体のcaptionに正しい文字があっても代用しません。単位は当該セルの接尾辞または対応見出しで照合し、矛盾・曖昧さは拒否します。棒グラフは当該行ラベルと共通単位で照合します。
- 表示されるv2 metricに非空の `label` が必要です。以前のv2でlabelを省略した数値原稿は、出典を再確認し表示名を明記して再検証してください。非表示の計算入力はlabelを必須にしません。既存3記事の完全一致ハッシュ例外は維持し、本文は変更しません。任意の自由文の数字を自動検算する保証ではありません。
- 新旧混在の表示順は **重要 → 通常 → 参考**、同重要度は公開絶対時刻の降順、同時刻は記事IDの昇順です。新しい通常記事が重要記事を追い越すことはありません。既存3記事のみの歴史的な版には既存の固定順序を適用します。importで配列順を確定し、buildは不正な順序を拒否します。UIの掲載開始以上・掲載終了未満のフィルターを維持し、期限切れ記事も正本から削除しません。
- 表示用date/reviewed_onはそれぞれ公開/確認日時をJSTへ変換して決定します。日付のみの対象期間はタイムゾーン変換しません。出来事の発表日、記事公開日時、原稿確認日時は別の意味として保持します。
- buildの評価時刻は既定で現在の絶対時刻、再現用には `python tools/build_site.py --as-of 2026-10-23T08:30:00+09:00` のように明示します。manifestの `as_of` はUTC、`delivery_date` はその瞬間のJST日付です。同原稿・同評価時刻なら順序・summary・manifest・ハッシュは一致します。
- 新着は「配信日の前日08:00 JST以降、評価時刻までに公開され、評価時刻に掲載対象の記事」です。前日の発表を翌朝掲載することを除外せず、「今日起きた事件」とは主張しません。掲載中でもこの範囲外は継続掲載、期限到達後は過去記事・期限切れ、開始前は掲載開始前です。新着/継続/期限切れ/開始前と掲載対象のID一覧をmanifestに記録します。要約は期限切れも明示ラベル付きで残す版の一覧であり、すべてを本日の新着と呼びません。
- 原稿版、各記事のrevision・hash、原稿生バイトhash、summary hash、配信基準時刻を対応づけます。公開照合はmanifestに固定された同じ基準時刻で再構築し、対象IDや区分の改変も不一致になります。サイトのリアルタイム掲載対象は閲覧時刻が進むと変化するため、照合成功は記録された時点のsnapshot一致です。

秘密情報/PIIチェックは既知のトークン形式、秘密鍵、認証付きURLなどの**ヒューリスティック**です。難読化、未知の秘密、自由文中のすべての個人情報は検出できず、誤検知もあります。自動公開の前提は担当者の出典照合と編集レビューであり、形式合格は「真実認定」ではありません。

作業ブランチで、UTF-8 JSONの単一記事を受け入れます（本番ファイルをテスト用に編集しない）。

```sh
python tools/editorial.py validate config/editorial.json
# 読み取った正本の生バイトSHA256とeditorial_versionを保持してから編集する。
sha256sum config/editorial.json
python tools/editorial.py import manuscript.json \
  --target config/editorial.json --mode create \
  --base-sha256 <読み取り時のSHA256> --base-version <読み取り時のeditorial_version> \
  --edition <新しいeditorial_version>
# 既存v2記事の更新は --mode update。revisionを1増やし、履歴を追記する。
python -m unittest discover -s tests -v
python tools/build_site.py
```

取り込みは全体を検証してから原子的に置き換えます。基点ハッシュ/版の不一致、ID重複、古いrevisionなどは拒否。置換前の拒否・書込み/置換失敗では正本のバイト列とハッシュを保持し、一時ファイルを除去します。原子的replaceがcommit点です。replace後のディレクトリfsync失敗は「拒否」ではなく `SaveCommittedError` / CLI終了コード2の **COMMITTED・耐久性UNKNOWN** として区別します。この場合は元ファイル不変と主張せず、対象を再読込して版とSHA256を確認し、自動再試行・自動rollbackをしません。停電等に対する永続化を確認できるまで運用判断を保留します。競合時は最新mainを取り直して差分をレビューし、原稿を再作成してください。強制push、自動上書き、失敗後の無条件再試行は禁止。ローカルのファイル保護はGitHub上の同時更新ロックではないため、GitHubへの保存時にも期待SHAと非強制更新を用います。

## ビルド・公開・会話配信

- `.site/data/editorial.json` は正本そのもの。`editorial-manifest.json` と `editorial-summary.txt` は同じ検証済み原稿から決定的に生成し、別に要約原稿を書きません。記事ID・版・ハッシュで対応づけます。
- `editorial-checks.yml` は作業ブランチpush/PRで単体テスト・ビルドと合成データのChromium表示試験を実施。読み取り権限のみでPages環境・Pagesアップロード・デプロイを持ちません。標準GitHub Actions runnerでPlaywright 1.62.0とChromiumを導入し、公開済み記事/合成データのスクリーンショット・報告だけを1日保持します（依存の導入以外、試験は外部ニュースを取得しません）。[Playwright公式：CI手順](https://playwright.dev/python/docs/ci)
- `editorial-delivery.yml` は**将来main採用後、mainの `config/editorial.json` 変更だけ**で公開。新しいスケジュールは追加しません。既存dailyの07:35/08:40 JSTのcron文字列はそのままです。
- RSSと詳報公開は `asa-brief-publish` の共通排他を使用。ロック取得後に最新mainをcheckoutし、保存/公開直前にリモートSHAを照合。RSSコミットは `git push origin HEAD:main` のみで、non-fast-forwardなら終了し、公開しません。キュー順に依存しません。
- RSSの `GITHUB_TOKEN` pushで別workflowが起動すると仮定せず、既存dailyの同一runでビルド・公開します。将来、別の自動処理が同トークンで詳報を書き込む場合もpush起動には依存せず、承認された明示的な公開経路が必要です。新しいトークンや権限拡張はこのPRの対象外です。[GitHub公式：イベント起動制約](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- 共通排他は他のGit pushを禁止するものではありません。公開直前/直後のSHAを照合し、間にmainが進んだ場合も「成功」と報告しません。チェックと公開の間の短い競合窓は残るため、承認後の運用では既存公開run終了まで編集mergeを待つ。旧イベントは最新mainを再検証してから公開します。待機runは置き換わることがあり、各イベントの実行保証はありません。[GitHub公式：同時実行制御](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)
- 公開直後にHTTPSのGitHub Pagesから記事・manifest・要約を取得し、期待した版/ID/ハッシュと照合。不一致・旧版・HTTP失敗を成功扱いしません。Pagesの伝播遅延は遅延、整合性破損は失敗として扱い、必要な再確認は承認済み操作で行います。

```sh
python tools/editorial_delivery.py verify \
  --expected .site/data/editorial-manifest.json \
  --base-url https://<owner>.github.io/<repo>/ \
  --status-output editorial-delivery-status.json
```

この実装は**ChatGPT/Dotsの任意の会話へ投稿しません**。`conversation_delivery=not_sent` を保持します。利用可能な製品機能・宛先・投稿権限を別途確認し、利用できなければDots担当者が検証済み要約と状態を指定会話に提示する代替運用です。記事公開成功、RSS取得成功、会話配信成功は別々の状態です。Actionsの緑色だけで全部の配信完了と判断しません。

## Phase 3A-Fix の検証記録と限界

Phase 2の128件およびChromium CI成功は過去HEADの実績であり、修正後HEADの保証には流用しません。以前の「ブラウザーCI待ち」は過去の作業時点の記録です。今回の受け入れ時には、**採用候補HEADそのもの**の `Editorial checks (no deployment)` のoffline/browser両jobのrun URL・終了状態・件数をPRに記録してください。未完了・失敗を成功と書かないでください。クラウド内Chromiumは既知のsandbox制約のため再試行・回避せず、許可済みの非デプロイCIを使用します。

Chromiumの320/375/390/430px試験はiPhone Safari実機、ホーム画面PWA、本番Service Worker更新・キャッシュ更新の成功を意味しません。これらはPhase 3B内で確認します。ニュースの出典真正性、実ニュースの編集品質、会話への通知到達も今回未検証です。

## 公開状態の判断

- **SUCCESS**：期待した原稿版・ID・記事ハッシュ・要約ハッシュ・配信基準時刻が公開先と一致。
- **DELAYED**：整合した別版、伝播待ち、取得不能。成功扱いにしない。
- **FAILED / DATA_MISMATCH**：同一版なのに異なる内容、ファイル混在、構造不正等。再公開前に原因確認。
- **UNKNOWN**：run終了や公開先の状態を確認できない。ActionsがSuccessでもサイト一致が未確認なら公開完了としない。

機械出力の `delayed` は取得不能も含み、運用上は公開状態UNKNOWNとして扱います。`conversation_delivery=not_sent` は常に未送信です。要約生成は会話配信成功ではありません。

## 停止・復旧手順（別途承認後に実行）

今回行うのは手順整備だけであり、workflow停止、Cancel、本番復旧は実行しません。

1. 不具合の観測時刻、期待/観測SHA・原稿版・ハッシュ、run URL、公開先の証拠を保存する。秘密情報は記録しない。
2. 承認された停止操作で**両方のpublisher `daily-news` と `editorial-delivery`**からの新規公開を停止する。片方のみでは公開が継続し得る。定期タスクの停止・変更にも別承認が必要。
3. 両workflowの実行中・待機runを列挙する。Cancel受付とrunの終了確認を区別する。終了未確認ならUNKNOWNとして重複再実行を禁止する。**Cancelは公開済みデータを元に戻さない**。
4. 正常版コードSHAと、そのとき公開された原稿/manifest/要約のハッシュを確認する。旧run再実行はcheckoutが最新mainを取得する場合があり、旧コード復元とは限らない。
5. 最新mainを取得し、原因差分と復旧対象（コード、原稿、公開成果物）を限定する。新しいRSS/アーカイブの更新を残し、リポジトリ全体を過去SHAへ巻き戻さない。
6. 最新mainから不具合差分のみを取り消す通常のrevert/fix PRを準備する。RSS自動更新を保持し、force push・破壊的rebase・main直接上書きをしない。
7. 最新mainとの統合、全テスト、原稿・要約・公開用データの整合性を検証しレビューする。
8. 人間が復旧対象、マージ、公開方法と再試行条件を明示承認する。
9. 承認された方法のみで再公開する。旧runの無条件再実行や未知状態のまま重複実行をしない。
10. 実際の公開先から取得して版・ID・全ハッシュを照合する。
11. iPhone Safariとホーム画面PWAで表示・保存・キャッシュ更新を確認する。
12. 証拠を基に人間が運用再開を判断する。停止解除も無断では行わない。

## Phase 3B 初回公開試験計画（別途人間承認後のみ）

1. 採用候補HEAD、Draft PR #1の差分/レビュー、最新mainとの統合、同HEADのCI成功、既存3記事とRSS保持を確認する。正常版SHAと公開データの復旧基準を記録する。
2. Pagesの公開先・設定・github-pages環境の対象を確認する。設定変更や権限変更が必要なら別承認を求める。
3. 本物のニュース原稿**1件**について一次情報・複数出典・数値対応・事実/分析/予測区分を人間がレビューする。発表日、確定日時、配信日、ID、revision、原稿ハッシュ、掲載期間、重要度を確定する。合成原稿を本番へ保存しない。
4. マージと公開を明示承認する。編集記事用push公開が直ちに起動しなくても、**次の既存daily-newsがマージ済み新コードを適用し得る**ため、マージと本番適用を完全に独立とは扱わない。既存公開run終了まで編集mergeを待つ。
5. 承認された方式で初回公開し、run URLと終了状態を確認する。公開先で原稿版・ID・revision・記事/原稿/要約ハッシュ、配信基準日時と対象を照合する。Actionsの緑だけでは完了にしない。
6. iPhone Safari実機とホーム画面PWAで今日/分野/決算/保存/設定の5タブ、図表、用語、出典、テーマ、文字サイズ、Service Worker更新と旧キャッシュからの遷移を確認する。
7. 同一原稿・同一配信基準時刻から生成された要約を確認し、承認済み通知先・権限で**一回のみ**通知試験する。未送信・遅延・失敗を区別する。
8. 失敗時は上記の両publisher停止・run確認・非破壊復旧手順に従う。人間が最終判定と運用再開を承認する。

毎朝08:00配信の定期タスク、cron変更、追加API/有料サービスは今回導入しません。GitHub Actionsの遅延・未実行があり厳密な08:00到着は保証しません。既存無料枠・利用制限は別途確認事項です。

**READY_FOR_PHASE3B_APPROVALはPhase 3B開始の人間承認を求められる状態であり、本番公開の承認ではありません。最終判定後は停止し、Phase 3Bを自動開始しません。** PRマージ、本番公開、実ニュース保存、通知、定期タスク設定は別途承認が必要です。
