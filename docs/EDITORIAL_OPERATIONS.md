# 朝のブリーフ：編集・配信契約（Phase 2）

このPRは準備用です。**マージ、本番公開、毎朝タスクの新設・変更は別承認**です。
`config/editorial.json` が詳報の唯一の正本。RSS の `data/latest.json`・アーカイブとは別に保持し、既存の画面・CSS・3記事を変更しません。追加のAI API・有料サービス・秘密鍵は不要です。

## 編集判断（Dots・レビュー担当者）

優先分野は、①日本株・投資・企業決算、②日本/世界経済・金融政策・金利・為替、③重大な国際情勢・政治・社会、④AI・半導体・重要技術、⑤重大なサイバーセキュリティ、⑥自治・税制・防災・生活制度、⑦その他の重大な社会的影響、の順です。ただし緊急性と読者への影響を優先し、分野の順位だけで採否を決めません。

候補ごとに重要性・影響範囲・新規性・読者との関連性・情報の信頼性を各0〜3点で記録し、`2×重要性 + 影響範囲 + 新規性 + 関連性 + 2×信頼性`（最大21点）と採否理由を残します。信頼性0点は採用しません。同点では一次資料が確認できるもの、次いで新規性を優先。同じ事件・決算は続報を既存IDに統合し、RSSの新着順・クリック数だけで選びません。この採否判断は編集作業であり、スキーマがニュース価値を保証するものではありません。

詳報は「何が起きたか／背景・経緯／仕組み／重要数値／複数の見方／投資・経済・社会への影響／今後の注目点／用語／出典」を扱います。該当しない項目は理由を記し、穴埋めの推測をしません。重要度に応じて文章量を調整し、比較表・棒グラフ・時系列を使います。表示対応は既存の `text`・`table`・`bars`・`flow`・`timeline` ブロックを再利用します。

- **事実**：出典中のどこで確認したかを明記。発表日時と確認日時を分ける。
- **分析**：筆者の解釈と明記し、根拠・異なる見方・限界を示す。
- **予測**：会社予想／市場予想／独自の見通しを区別し、前提と不確実性を示す。未来を事実扱いしない。
- **決算**：連結範囲、対象期間、通貨・桁、実績／会社予想／市場予想を揃えて比較。前年同期と直前四半期、累計と単独を混同しない。日経225採用は公式構成銘柄を確認し、会社名・記事から推測しない。市場予想が未確認なら「未確認」とし、超過・未達を判定しない。
- 重要数値は出典と構造化メタデータを対応づけ、算出値は計算式・入力・単位・丸め精度を残す。未確認の重要数値を確定事実として掲載しない。
- 未公開の個人情報・投資情報・認証情報を原稿やログに含めない。機械的な検出だけに頼らず、人間が公開対象を確認する。

## 原稿の受け入れと判定

既存JSONの描画フィールドを維持し、新規原稿にはv2の確認・更新履歴・分類・数値メタデータを付けます。正確な必須項目と合成見本は `tools/editorial.py` とそのテストを正とします。既存3記事の特例は記事ごとの完全一致ハッシュに限定し、同じIDの改変や新記事に旧形式を流用して検査を回避できません。

判定を混ぜません。`sourcecheck.status=passed` は照合担当者の記録要件の合格であり、`source_truth=not_verified_by_program` を明示します。`editorial_judgment=recorded_attestation` も人による判断の記録です。既存3記事の免除から新たな照合済み判定は導きません：

| 判定 | 検証するもの | 保証しないもの |
|---|---|---|
| 形式 | 必須項目・型、ID、日時/TZ/順序/期限、URL、参照番号、表の形、重複 | 記事の真実性 |
| 数値整合性 | 有限の数値、単位/期間/実績・予想、算出値の再計算 | 元の数値が出典と一致すること |
| 出典照合 | 担当者の照合結果・根拠・確認日時を記録 | 自動でリンク先を読んだ、真偽を確認したという保証 |
| 編集判断 | 採用/保留、根拠、不確実性・見方の区別を記録 | ニュース解釈や投資判断の正しさ |

新規ブロックの見出しに `事実`・`分析`・`予測` を明記し、既存画面のまま区別を表示します。数値表の各数値セルは `numeric_cells`、棒グラフの各行は `metric_ids` で `metrics` に結び、表示値・単位・期間・実績/会社予想/市場予想の表示を一致させます。`ratio_percent`・`growth_percent`・`difference`・`sum` は2入力を再計算し、指定桁の四捨五入（half-up）と照合。%同士の差はptです。自由文の数字の完全抽出・真偽・因果関係は自動保証せず、未確認の構造化数値は掲載拒否します。対象期間を持つ数値には期首/期末を、金額には通貨を必須とします。受け入れJSONは2MB以下です。期限切れの保管記事は保持しますが、追加/更新する対象の期限切れは拒否します。

秘密情報/PIIチェックは既知のトークン形式、秘密鍵、認証付きURLなどの**ヒューリスティック**です。難読化、未知の秘密、自由文中のすべての個人情報は検出できず、誤検知もあります。自動公開の前提は担当者の出典照合と編集レビューであり、形式合格は「真実認定」ではありません。

作業ブランチで、UTF-8 JSONの単一記事を受け入れます（本番ファイルをテスト用に編集しない）。

```sh
python tools/editorial.py validate config/editorial.json
# 読み取った正本の生バイトSHA256とeditorial_versionを保持してから編集する。
sha256sum config/editorial.json
python tools/editorial.py import manuscript.json \
  --target config/editorial.json --mode create \
  --base-sha256 <読み取り時のSHA256> --base-version <読み取り時のeditorial_version> \
  --edition <新しいeditorial_version>
# 既存v2記事の更新は --mode update。revisionを1増やし、履歴を追記する。
python -m unittest discover -s tests -v
python tools/build_site.py
```

取り込みは全体を検証してから原子的に置き換えます。基点ハッシュ/版の不一致、ID重複、古いrevisionなどは拒否。失敗時は正本を保持します。競合時は最新mainを取り直して差分をレビューし、原稿を再作成してください。強制push、自動上書き、失敗後の無条件再試行は禁止。ローカルのファイル保護はGitHub上の同時更新ロックではないため、GitHubへの保存時にも期待SHAと非強制更新を用います。

## ビルド・公開・会話配信

- `.site/data/editorial.json` は正本そのもの。`editorial-manifest.json` と `editorial-summary.txt` は同じ検証済み原稿から決定的に生成し、別に要約原稿を書きません。記事ID・版・ハッシュで対応づけます。
- `editorial-checks.yml` は作業ブランチpush/PRで単体テスト・ビルドと合成データのChromium表示試験を実施。読み取り権限のみでPages環境・Pagesアップロード・デプロイを持ちません。標準GitHub Actions runnerでPlaywright 1.62.0とChromiumを導入し、公開済み記事/合成データのスクリーンショット・報告だけを1日保持します（依存の導入以外、試験は外部ニュースを取得しません）。[Playwright公式：CI手順](https://playwright.dev/python/docs/ci)
- `editorial-delivery.yml` は**将来main採用後、mainの `config/editorial.json` 変更だけ**で公開。新しいスケジュールは追加しません。既存dailyの07:35/08:40 JSTのcron文字列はそのままです。
- RSSと詳報公開は `asa-brief-publish` の共通排他を使用。ロック取得後に最新mainをcheckoutし、保存/公開直前にリモートSHAを照合。RSSコミットは `git push origin HEAD:main` のみで、non-fast-forwardなら終了し、公開しません。キュー順に依存しません。
- RSSの `GITHUB_TOKEN` pushで別workflowが起動すると仮定せず、既存dailyの同一runでビルド・公開します。将来、別の自動処理が同トークンで詳報を書き込む場合もpush起動には依存せず、承認された明示的な公開経路が必要です。新しいトークンや権限拡張はこのPRの対象外です。[GitHub公式：イベント起動制約](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- 共通排他は他のGit pushを禁止するものではありません。公開直前/直後のSHAを照合し、間にmainが進んだ場合も「成功」と報告しません。チェックと公開の間の短い競合窓は残るため、承認後の運用では既存公開run終了まで編集mergeを待つ。旧イベントは最新mainを再検証してから公開します。待機runは置き換わることがあり、各イベントの実行保証はありません。[GitHub公式：同時実行制御](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)
- 公開直後にHTTPSのGitHub Pagesから記事・manifest・要約を取得し、期待した版/ID/ハッシュと照合。不一致・旧版・HTTP失敗を成功扱いしません。Pagesの伝播遅延は遅延、整合性破損は失敗として扱い、必要な再確認は承認済み操作で行います。

```sh
python tools/editorial_delivery.py verify \
  --expected .site/data/editorial-manifest.json \
  --base-url https://<owner>.github.io/<repo>/ \
  --status-output editorial-delivery-status.json
```

この実装は**ChatGPT/Dotsの任意の会話へ投稿しません**。`conversation_delivery=not_sent` を保持します。利用可能な製品機能・宛先・投稿権限を別途確認し、利用できなければDots担当者が検証済み要約と状態を指定会話に提示する代替運用です。記事公開成功、RSS取得成功、会話配信成功は別々の状態です。Actionsの緑色だけで全部の配信完了と判断しません。

## Phase 3 初回配信試験（承認後のみ）

1. 人間がDraft PRの差分・テスト・既存3記事の一致・出典/編集判断をレビューする。マージと初回本番公開、対象原稿、公開予定時刻、失敗時の対応を**明示承認**する。これらはPhase 2に含まれない。
2. mainの最新SHAを再取得し、ブランチとの差を確認。合成原稿はローカル一時ディレクトリ/CIのみで検証し、本番正本に入れない。全テスト・ビルド・不正入力拒否・競合拒否を再実行する。
3. Pagesの設定とgithub-pages環境がmainのみを許可すること、対象が公開リポジトリであることを確認。必要な設定変更は別承認。承認されたマージ後、内容と出典を人間が確認した本物の原稿を基点SHA付きで作業ブランチに取り込み、レビュー後にmainへ反映する。
4. mainの詳報pushが公開workflowを起動することを確認。RSSと重なっても共通排他を維持し、non-fast-forward/古いSHAなら中断。無断のforce-pushや権限回避をしない。
5. runのPages URLで期待版・記事ID・ハッシュ・要約の一致を確認。iPhone/Safariで今日/分野/決算/保存/設定、図表・出典・用語・文字サイズを確認する。既存Service Workerや端末キャッシュが旧表示なら更新して再確認する。
6. 指定会話への投稿機能と権限を確認してから、同じ生成済み要約と検証済み状態を配信。未投稿・伝播待ち・失敗をそのまま通知し、成功を装わない。
7. 失敗なら旧版を勝手に上書きせず原因と期待/観測版を残し、最新mainから安全に再試験する。本番の復旧変更・再公開は承認範囲を確認する。

残る承認事項：PRマージ、本番公開（初回と再試行方針）、実原稿の採用、任意会話の投稿先/機能/権限、毎朝のDots編集・配信タスク導入。08:00到着はActionsや配信先の遅延があり保証できません。Phase 2では本番公開・実ネットワークでの出典照合・実機iPhone・実会話自動投稿は未実施です。

ブラウザー検証の現状：クラウド作業環境ではChromium起動がソケットのsandbox制約で停止し、表示試験は未完了です。制約回避や同環境での再試行は行わず、上記の独立した標準CI runnerに試験を用意しました。CIの完了証跡を確認するまでは「CI待ち」であり、合格とは扱いません。
